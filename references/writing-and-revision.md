# Requested Revision and Writing

Use this reference only for an explicit request to restructure existing manuscript text or draft new manuscript content. These are ordinary-language tasks, not mandatory user-selected modes.

Apply the existing `polishing-rules.md` and `release-principle.md` throughout. Keep the original workflow's revised-text-only default, scientific-meaning protections, and execution permissions.

## Revise Existing Text

1. Identify the requested scope from the user's instruction: a sentence, paragraph, section, argument order, emphasis, or length. Use an obvious interpretation without a setup questionnaire.
2. Read the relevant manuscript context and available evidence. Do not repeat a completed project audit unless affected files have changed.
3. Make only changes needed for the stated goal. A request to "improve the logic" allows the necessary local reordering; it does not authorize unrelated sections, source-file edits, changed results, or new experiments.
4. Keep paragraph boundaries by default. Change them when the user asks for restructuring or the original logic genuinely requires it.
5. Use the project's supported contribution and the existing Presentation-First Narrative Principle. Preserve technical terms, numbers, citations, assumptions, and the strength and scope of claims.
6. Do not silently add technical claims merely because they appear elsewhere in the project. Add supporting material only when the requested substantive revision calls for it and the available evidence supports it.
7. Return the revised text only, unless the user requested a different output format.

## Draft New Manuscript Text

1. Use the requested section, purpose, length, and language. Infer straightforward defaults from the project and request instead of asking the user to fill out a form.
2. Ground the draft in supplied notes, reviewed manuscript content, code that was actually inspected, and existing evidence. Code may support a description of implementation, but it does not independently verify experimental outcomes.
3. Internally organize the requested passage, then write it directly. Show an outline first only when requested. For abstracts and introductions, retain the original problem -> gap -> idea -> strongest supported evidence sequence.
4. Use section-appropriate emphasis: definitions and assumptions for methods, comparison conditions and observations for experiments, and supported takeaways for conclusions. This refines application of the existing rules; it does not replace them.
5. Do not invent results, causal explanations, significance claims, novelty claims, baselines, references, or completed experiments. Do not describe planned work as completed work.
6. When a missing detail is optional, omit it rather than inventing it. When a missing fact is essential, use the existing uncertainty exception and ask one focused question. Use explicit placeholders only when the user requests a scaffold or provisional draft.
7. Return the requested manuscript text only. Supply LaTeX when requested or when extending a supplied LaTeX passage; do not automatically edit files.

## Final Silent Check

Before sending either output, check:

- numbers, units, negation, conditions, uncertainty, and comparison scope have not drifted;
- mathematical content, citation keys, labels, and cross-references are preserved;
- new factual statements in a draft or substantive revision are supported by supplied or inspected material;
- the requested section and length are respected without deleting essential meaning;
- the response contains only the requested deliverable, except for a necessary clarification.

Do not print this checklist. Keep already clear wording when changing it would not improve the requested result.
